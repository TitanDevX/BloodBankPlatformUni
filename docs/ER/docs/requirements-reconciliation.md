# Requirements reconciliation — 27 October 2026

This update closes the review findings in the ERD and class design together. Existing entity/attribute identifiers and types are preserved; new fields/records are additive. Backend implementation, migrations and data backfill are separate work.

- **FR-18/19:** Persist one `requests.addressed_bank_id` and submission match timestamp/policy after revalidation. Keep optional `accepted_bank_id` for its original later decision meaning. A static nearest-bank search over criteria makes no submitted row/reservation; no match creates none. A successful submitted destination must supply the full exact component/ABO/Rh quantity at revalidation time.
- **FR-20:** Accept only pending requests and reserve exactly the full quantity atomically. Require accepting bank to equal addressed bank. Reevaluate similar pending requests at that bank using remaining stock; reject insufficient ones automatically without partial reservations. Keep manual/automatic source, reason and time, and require a staff actor only for manual rejection. Accepted and rejected audit values are mutually exclusive. No delivery inference is introduced.
- **FR-16/17:** Assign record-processing and availability-reevaluation operations. Collection/separation and laboratory paths can finish independently; release requires both successful separation/accepted processing and passed, verified laboratory screening. Actor/time information remains on collection/separation/component fields as described in the class design. A new per-component multi-technician workflow would need its own actor/history design.
- **FR-18/23:** Bank notice worklists expose pending addressed requests and expired undisposed components to authorized inventory staff. Current-expiry checks prevent allocation independently of notice/task success. No new read-receipt, email/SMS or notice-history requirement is invented.
- **FR-21/22:** `forecast_runs` owns bank/requester scope, immutable cutoff/target/data/model/snapshot provenance and a result manifest. `demand_forecasts` contains daily expected quantities and optional validated intervals. Composite idempotency/point uniqueness, explicit unavailable manifest entries, preparation-null/publication-required provenance and atomic publication guard results. Saved retrieval cannot recalculate or substitute another run, and forecasting cannot alter stock/requests.
- **Demand attribution:** Original submitted quantities count against the addressed bank, including later rejected requests. Submission facts are immutable in the current workflow. No-match/cancelled searches are not saved demand. Do not backfill historical attribution from a current nearest-bank query or merely from an accepted-bank field. If later correction/rerouting policy is introduced, add explicit events rather than overwriting originals.

The architecture's request sequence and forecasting plan are synchronized with these records. The detailed use-case text governs match-before-submission; the older full-flow image remains illustrative and is not silently presented as a step-accurate revised flow. Offline synchronization stays separate as the user requested; run completeness fields do not claim to implement it.
